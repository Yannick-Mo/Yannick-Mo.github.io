📘 LangGraph 完整学习笔记

一、概述

1.1 什么是 LangGraph？

LangGraph 是 LangChain 团队开发的开源框架，用于构建有状态的、多角色 LLM 智能体应用。它将智能体工作流建模为有向图，通过节点（Nodes）、边（Edges）和状态（State）三大核心组件，实现复杂、可控、可中断的 AI 工作流编排。

1.2 核心设计理念

LangGraph 的核心设计理念是帮助开发者在智能体工作流中添加更好的精确性和控制。与传统的线性 Chain 相比，LangGraph 的优势在于：

特性 说明
图结构建模 支持分支、循环、并行等复杂控制流
状态驱动 所有决策基于明确定义的状态
可中断与可恢复 支持 Human-in-the-Loop 和断点续传
可观测性 原生集成 LangSmith 追踪调试
多智能体协作 支持构建多智能体协同系统

二、核心概念

LangGraph 的核心是将智能体工作流建模为图（Graph）。图由三个关键组件定义：State、Nodes、Edges。

2.1 State（状态）

State 是一个共享的数据结构，表示应用程序的当前快照。它贯穿整个执行流程，所有节点的输入和输出都基于 State。

  • 定义方式：通常使用 TypedDict 或 Pydantic BaseModel 定义
  • Reducer 函数：指定如何将节点的更新应用到 State 上
  • 作用：State 的模式（Schema）是图中所有 Nodes 和 Edges 的输入模式

from typing import TypedDict, Annotated
import operator

class State(TypedDict):
    messages: Annotated[list[str], operator.add]  # 使用 reducer 追加
    intent: str
    resolved: bool

2.2 Nodes（节点）

Nodes 是编码智能体逻辑的Python 函数。它们接收当前 State 作为输入，执行计算或副作用，并返回一个字典，返回的字典中的键（key）必须是你在状态（State）中定义过的字段。

  • 本质：节点就是普通的 Python 函数——可以包含 LLM，也可以只是纯代码
  • 常见类型：LLM 节点、工具节点、人工节点、路由节点
  • 执行模型：节点通过消息传递机制通信

def my_node(state: State) -> dict:
    # 读取状态
    last_msg = state["messages"][-1]
    # 执行逻辑...
    # 返回状态更新（部分更新即可）
    return {"intent": "refund", "resolved": True}

2.3 Edges（边）

Edges 是决定接下来执行哪个 Node 的函数。

  • 固定边（Fixed Edge）：无条件跳转到指定节点
  • 条件边（Conditional Edge）：根据当前 State 动态决定目标节点

# 条件边

    return "refund" if state["intent"] == "refund" else "general"

graph.add_conditional_edges("classify", route_by_intent)

2.4 执行模型：超步（Super-step）

LangGraph 的底层算法受 Google Pregel 系统启发，程序以离散的超步（Super-step） 进行：

  1. 所有节点初始为 inactive（非活跃） 状态
  2. 节点在收到传入边的新消息（状态）后变为 active（活跃）
  3. 活跃节点执行其函数并返回更新
  4. 每个超步结束时，无消息的节点标记为 inactive
  5. 所有节点 inactive 且无消息传输时，图执行终止

并行与串行：并行运行的节点属于同一个超步，串行运行的节点属于不同的超步。

四、持久化与记忆（Persistence & Memory）

LangGraph 提供两套互补的持久化系统：Checkpointer（检查点） 负责短期、线程内的状态快照；Store（存储） 负责长期、跨线程的应用数据。两者共同构成了 LangGraph 的完整持久化层。

4.1 Checkpointer（检查点）—— 短期记忆

Checkpointer 在每个超步（Super-step）保存图状态的快照（Checkpoint）。

核心作用

  • 对话连续性：通过 thread_id 恢复历史对话上下文
  • Human-in-the-Loop：支持人工介入后从中断点恢复执行
  • 时间旅行（Time Travel）：可以回溯到任意历史状态，进行调试或分支探索
  • 故障恢复：应用崩溃后可从最近的检查点恢复

工作原理

Checkpointer 在每个超步结束时自动保存状态，无需手动调用。它通过检查点元数据（包括 thread_id、checkpoint_id、parent_checkpoint_id）构建状态版本树，支持任意节点的回溯。

⚠️ 注意：InMemorySaver 将检查点存储在 RAM 中，进程重启后数据丢失，仅适用于开发测试。生产环境务必使用持久化后端。

4.2 Store（存储）—— 长期记忆

Store 持久化图状态之外的应用定义数据，提供跨线程、跨用户的长期记忆能力。

核心概念

  • Namespace（命名空间）：类似文件夹，用元组分层组织数据，如 ("user_123", "memories") 或 ("org_456", "preferences")
  • Key（键）：在命名空间内唯一标识一条数据，如 "food_preference"
  • Value（值）：存储的实际数据，以 JSON 文档（dict） 形式保存

每个存储项自动附带 created_at 和 updated_at 时间戳元数据。

from langgraph.types import RunnableConfig
from langgraph.store.base import BaseStore
from langgraph.graph import MessagesState

def call_model(
    state: MessagesState,
    store: BaseStore,  # 注入 Store
    config: RunnableConfig
):
    """节点：调用模型并读写长期记忆"""
    user_id = config.get("configurable", {}).get("user_id", "default_user")
    namespace = (user_id, "memories")

    # 读取该用户的所有记忆
    memories = store.search(namespace)

    # 将记忆整合进系统提示词
    memory_text = "\n".join([f"- {item.value}" for item in memories])

    # 生成回复...
    response = model.invoke([...])

    # 将新信息写入 Store
    store.put(
        namespace,
        "new_insight",
        {"key": "value", "timestamp": datetime.now().isoformat()}
    )

    return {"messages": [response]}

4.3 Checkpointer vs Store 完整对比

维度 Checkpointer Store
持久化内容 图状态的快照（State Snapshot） 应用定义的键值数据（JSON 文档）
作用范围 单个线程（Thread） 跨线程（Cross-thread）、全局
记忆类型 短期、线程级记忆（Short-term） 长期、跨线程记忆（Long-term）
主要用途 对话连续性、HITL、时间旅行、容错 用户偏好、事实信息、共享知识
生命周期 随线程自动管理，超步结束自动保存 应用代码显式读写，手动管理
访问方式 通过 thread_id 自动管理 通过 namespace + key 显式读写
数据结构 图状态的对象/字典 命名空间 + 键值对（JSON 文档）
搜索能力 按时间/线程索引查询 精确查询 + 语义向量搜索
生产后端 PostgresSaver、MongoDBSaver PostgresStore、MongoDBStore
开发者注释 类似 Agent 的 Git 版本控制 类似 Agent 的长期记忆库

类比理解

  • Checkpointer = Agent 的 Git：提交（Commit）状态的快照，可以在分支间切换（时间旅行），支持合并和回溯。
  • Store = Agent 的 笔记/数据库：存储跨会话的知识，可以随时查询、更新、搜索。

五、流式输出（Streaming）

流式输出是 LangGraph 的核心能力之一，它允许在 Agent 执行过程中逐步输出中间结果，而非等待整个流程完成后再一次性返回。

5.1 为什么需要流式输出？

场景 非流式（阻塞） 流式（增量）
用户体验 等待数秒甚至数十秒才能看到回复 实时看到 LLM 逐词生成，类似 ChatGPT
长时间任务 用户无法感知进度，可能以为系统卡死 可展示中间步骤、工具调用、进度信息
调试开发 只能看到最终状态，难以定位问题 可观察每个超步的状态变化，便于调试
人机协同 无法在中间介入 可在关键节点暂停，等待人工反馈后再继续

5.2 Stream Modes（流模式）

模式 描述 输出内容 适用场景
values 每步之后的完整 State 整个状态对象 需要完整上下文，不关心具体变更细节
updates 每步之后的状态增量更新 仅变更的字段 监控状态变化，节省带宽
messages LLM 调用的逐 Token 输出 增量文本片段（Token） 实现打字机效果，实时展示 LLM 回复
custom 节点通过 writer 发出的自定义数据 开发者自定义的消息 进度报告、调试信息、中间结果
tools 工具调用的生命周期事件 工具调用开始、进行中、完成等事件 追踪工具执行状态
debug 所有可用信息（调试用） 完整的执行日志 开发调试、问题排查

5.4 values vs updates 详解

values 模式

  • 输出时机：每个超步（Super-step）结束后
  • 输出内容：该时刻的完整状态
  • 特点：每次输出都包含全量状态，适合需要完整上下文的场景
1
2
3

超步 0: {"messages": [...], "user_info": None, "step": 0}
超步 1: {"messages": [...], "user_info": "张三", "step": 1}
超步 2: {"messages": [...], "user_info": "张三", "step": 2, "result": "完成"}

updates 模式

  • 输出时机：每个节点执行完毕后
  • 输出内容：该节点对状态做的增量更新
  • 特点：只输出变更部分，带宽更小，适合关注"谁改了什么东西"
1
2
3

node_A: {"user_info": "张三"}
node_B: {"result": "处理中..."}
node_C: {"result": "完成"}

5.13 常见陷阱与最佳实践

❌ 常见陷阱

  1. 混淆 values 和 updates 的输出格式：values 直接返回状态对象；updates 返回 {node_name: update_dict}
  2. 在 messages 模式下忽略 metadata：元数据包含了节点信息、消息 ID 等，用于区分来源
  3. 忘记设置 LLM 的 streaming=True：messages 模式依赖 LLM 客户端的流式能力
  4. 在非 LLM 节点使用 messages 模式：非 LLM 节点不会产生 Token 输出

6.1 Human-in-the-Loop（人机协作）

HITL 是 LangGraph 最核心的高级特性之一，它让 Agent 在执行关键操作前 暂停执行，等待人工审批或输入。

核心原理

HITL 基于 Checkpointer 实现。当节点调用 interrupt() 时，LangGraph 会：

  1. 保存当前状态（包括图中所有节点的进度）
  2. 暂停执行，返回 interrupt 信息给调用方
  3. 之后通过 Command(resume=...) 恢复执行，并从暂停点继续

from langgraph.types import interrupt

def approval_node(state: State) -> State:
    """需要人工审批的节点"""
    proposed_action = state.get("proposed_action")

    # 1. 暂停执行，等待人工输入
    user_response = interrupt({
        "question": "是否执行此操作？",
        "action": proposed_action,
        "details": "此操作将删除用户数据，请确认"
    })

    # 2. 收到用户响应后继续执行
    approved = user_response.get("approved", False)
    state["approved"] = approved
    state["status"] = "executing" if approved else "rejected"
    return state

6.3 Command API（命令模式）

Command 是 LangGraph 推荐的路由和控制模式，相比条件边（Conditional Edge），它更简洁、功能更强，支持同时更新状态和控制流。

  • 原地跳转：直接从当前节点跳转到任意节点（或 END）
  • 状态更新：在跳转的同时更新状态
  • 子图控制：可以从子图向父图传递命令
  • 支持在节点、条件函数、错误处理器中使用

    else:

# 定义中间件：记录节点执行时间
class TimingMiddleware(Middleware):
    def __call__(self, next_node):
        def wrapped(state, config):
            import time
            start = time.time()
            result = next_node(state, config)
            elapsed = time.time() - start
            print(f"节点执行耗时: {elapsed:.2f}秒")
            return result
        return wrapped

# 应用中间件
agent = Agent(
    model="gpt-4",
    tools=[...],
    middlewares=[TimingMiddleware()]
)

中间件 vs 节点内逻辑

维度 中间件 节点内逻辑
作用范围 图级别，所有节点生效 单个节点
修改图结构 不修改 不修改
代码复用 高，一次编写多处复用 低，需要每个节点重复
测试难度 较难（需要图上下文） 容易（纯函数）
适用场景 横切关注点（日志、监控等） 业务逻辑

最佳实践：将基础设施类功能放在中间件中，将业务逻辑放在节点内。

class ErrorHandlingMiddleware(Middleware):
    def __call__(self, next_node):
        def wrapped(state, config):
            try:
                return next_node(state, config)
            except RateLimitError as e:
                return {"error": "rate_limited", "retry_after": e.retry_after}
            except (TimeoutError, ConnectionError) as e:
                return {"error": "service_unavailable", "message": "请稍后重试"}
            except Exception as e:
                logger.error(f"节点执行异常: {e}")
                return {"error": "internal_error"}
        return wrapped

6.5 高级特性总结

特性 核心用途 关键 API 推荐版本
Human-in-the-Loop 人工审批、敏感操作确认 interrupt(), Command(resume=...) v0.0.x
子图（Subgraph） 模块化、团队协作、状态隔离 StateGraph 嵌套 v0.0.x
Command API 声明式路由、状态跳转 Command(goto=..., update=...) v0.2.x+
中间件（Middleware） 日志、监控、鉴权、限流 .with_middleware(), Middleware v0.4+

6.6 最佳实践与注意事项

  1. HITL 设计：中断信息应清晰、结构化，便于前端展示；恢复逻辑要考虑用户拒绝的情况。
  2. 子图设计：保持子图职责单一，输入输出明确；子图状态不应与父图过度耦合。
  3. Command 使用：优先使用 Command 替代条件边，特别是在复杂路由场景中。
  4. 中间件使用：不要在中间件中修改核心业务状态，仅用于横切关注点。
  5. 版本兼容：注意中间件 API 在不同版本间的差异，查阅官方文档确认。
  6. 测试：HITL 和子图功能依赖 Checkpointer，测试时确保检查点存储正确配置。

这些高级特性共同构成了 LangGraph 从"简单工作流"到"生产级 Agent 系统"的完整能力。合理运用它们，可以构建出具备人工协作、模块化架构、清晰控制和可观测性的复杂 Agent 应用。
