TCP 核心机制整理笔记

一、TCP 头部详解

TCP 头部长度在 20 字节（固定） 到 60 字节 之间（含可变选项）。

1. 源端口（第1-2字节）——16位

  • 表示什么：发送端应用程序的端口号。
  • 作用：配合 IP 地址，唯一标识发送端的进程（如浏览器随机生成的 64623 端口）。

2. 目的端口（第3-4字节）——16位

  • 表示什么：接收端应用程序的端口号。
  • 作用：告诉操作系统把数据交给哪个进程（如 Web 服务器的 80 或 443 端口）。

3. 序列号（第5-8字节）——32位

  • 表示什么：本报文段所发送数据的第一个字节在整个字节流中的编号（初始序列号 ISN 在握手时随机生成）。
  • 作用（核心）：
    1. 按序重组：接收方根据 Seq 号把乱序到达的包拼回原样。
    2. 去重：如果收到相同 Seq 号的包，直接丢弃重复项。
    3. 三次握手中的关键：SYN 包消耗一个 Seq 号，所以后续数据包的 Seq = 初始 Seq + 1。

4. 确认号（第9-12字节）——32位

  • 表示什么：期望接收到的下一个字节的序列号。
  • 作用（核心）：
    • 它等于已成功接收到的最后一个字节的 Seq 号 + 1。
    • 只要 ACK 标志位为 1（除握手第一个包外，几乎所有包都带 ACK），该字段有效。
    • 表示：“确认号 之前的所有字节我都收到了，请从 确认号 这个位置开始发下一个”。

5. 数据偏移（第13字节 高4位）——4位

  • 表示什么：TCP 头部的总长度（以 4 字节 为单位）。
  • 作用：因为头部有可变选项，接收方需要靠这个值知道“头部在哪结束，数据从哪开始”。
  • 取值：最小值为 5（即 5×4=20 字节），最大值为 15（即 15×4=60 字节）。

6. 保留位（第13字节 中3位）——3位

  • 目前全为 0，保留给未来使用。

7. 标志位（第13字节低1位 + 第14字节高8位）——共9位

用于控制连接状态和数据传输行为。最常用的是后 6 位（URG、ACK、PSH、RST、SYN、FIN）：

  • URG（紧急）：置 1 时，紧急指针字段有效，数据需优先处理（现已很少用）。
  • ACK（确认）：置 1 时，确认号字段有效。除了握手第一个 SYN 包，其他所有包必须置 1。
  • PSH（推送）：置 1 时，接收方应尽快将数据交给应用层，而不必等缓冲区满了再交（极少强制）。
  • RST（重置）：置 1 时，强制中断连接（用于报错、拒绝非法请求、主机崩溃重启）。
  • SYN（同步）：置 1 时，表示发起连接（握手第一步）或接受连接（握手第二步）。
  • FIN（结束）：置 1 时，表示发送方没有数据要发了，请求关闭连接（四次挥手）。

另外还有 CWR 和 ECE 两个标志位用于显式拥塞通知（ECN），较少在基础面试中展开。

8. 窗口大小（第16-17字节）——16位

  • 表示什么：发送本报文段的那一方，当前接收缓冲区剩余的可用空间大小（以字节为单位）。
  • 作用（核心）：流量控制。接收方告诉发送方：“你最多还能给我发这么多字节，别把我撑死。”
  • 注意：这是“滑动窗口”机制的核心字段，值受限于 16 位最大值 65535。但通过窗口缩放选项（Window Scale），实际值可左移位数，达到 GB 级别。

9. 校验和（第18-19字节）——16位

  • 表示什么：发送端计算出的校验码。
  • 作用（核心）：端到端的数据完整性校验。
  • 覆盖范围：不仅校验 TCP 头部+数据，还校验一个伪头部（Pseudo Header）（包含源 IP、目的 IP、协议号、TCP 长度）。这保证了数据没有在传输中被篡改，且 IP 地址没有送错。

10. 紧急指针（第20-21字节）——16位

  • 表示什么：只有当 URG 标志置 1 时有效。它指向“紧急数据”的最后一个字节在数据流中的偏移量（正数）。
  • 作用：配合 URG 标志，让接收方跳过普通数据，先读紧急数据（如 Ctrl+C 中断指令）。现代应用层协议已基本不依赖此机制。

11. 选项（第21字节之后，可变部分）——长度 0~40 字节

  • 表示什么：用于扩展 TCP 功能的额外参数，必须为 4 字节的整数倍（不足补 0）。
  • 最常用的内容：
    1. MSS（最大报文段长度）：在握手 SYN 包中告知对方，自己能接收的最大 TCP 数据载荷长度（不含头），避免 IP 分片。
    2. 窗口缩放（Window Scale）：在握手时协商左移位数，让窗口大小突破 65535。
    3. 时间戳（Timestamp）：用于计算往返时间（RTT）和防止序列号回绕（PAWS）。
    4. SACK 允许（Selective Acknowledgment）：支持选择性重传，只重传丢失的包，而非重传所有后续数据。

二、三次握手与四次挥手

2.1 三次握手及头部变化

阶段 核心头部字段变化
第一次（SYN） Seq=随机 ISN（如 100），ACK 标志=0（因为无确认号），SYN=1，携带 MSS/窗口缩放等选项（头部约 40 字节）。
第二次（SYN+ACK） Seq=服务器随机 ISN（如 500），Ack=101（客户端 Seq+1），SYN=1, ACK=1，携带选项。
第三次（ACK） Seq=101，Ack=501（服务器 Seq+1），ACK=1（SYN=0），不再携带选项（头部仅 20 字节），窗口字段告知接收缓冲区大小。

2.2 四次挥手（连接释放）详解

与三次握手“同时发 SYN+ACK”不同，四次挥手之所以是四次，核心原因是：TCP 是全双工通信，双方都要独立关闭自己的发送方向。且被动关闭方（通常是服务端）收到 FIN 后，可能还有数据要发，所以 ACK（回应） 和 FIN（关闭请求） 必须分开发送。

注意：如果被动关闭方恰好也没有数据要发了，两次挥手（ACK+FIN 合并）也可以，称为三次挥手（但标准模型依然按四次描述）。

流程详解（以客户端主动关闭为例）

次数 发送方 → 接收方 核心头部标志位 序列号/确认号变化 发送方状态变迁 接收方状态变迁
第一次 客户端 → 服务端 FIN=1, ACK=1（通常带 ACK） Seq=u（u 等于客户端最后发送数据的最后一个字节序号+1）

关键头部字段在挥手时的特殊表现

  1. FIN 标志位：值为 1 时，表示“我的数据发完了，请求关闭我这个方向的传输”。
  2. 序列号（Seq）消耗规则：FIN 和 SYN 一样，都要消耗掉一个序列号。
    • 第一次挥手：Seq=u，这个 FIN 本身占 1 个字节的序列号空间，所以第二次挥手的 ACK 必须是 Ack=u+1。
    • 第三次挥手：Seq=w（服务端的 FIN 也占一个号），第四次挥手的 ACK 必须是 Ack=w+1。
  3. 第二次挥手（纯 ACK）：和三次握手中的第三次 ACK 一样，通常不带任何 TCP 选项，头部仅 20 字节。

核心状态机详解

  • FIN_WAIT_1：客户端发出第一次 FIN 后进入。若收到服务端的 FIN+ACK（即服务端同时应答并关闭，极少数情况），可直接跳至 TIME_WAIT。
  • CLOSE_WAIT（危险区）：服务端收到 FIN 并回复 ACK 后进入。此时服务端还能继续向客户端发数据。如果程序有 Bug（如未调用 close()），连接会长期卡在此状态，造成句柄泄漏。
  • FIN_WAIT_2：客户端收到第二次挥手的 ACK 后进入。此时客户端只收不发，等待服务端的第三次挥手（FIN）。如果服务端一直不发 FIN，客户端会通过保活计时器或超时强行断开。
  • LAST_ACK：服务端发出自己的 FIN 后进入。等待客户端的最后一个 ACK 确认，若超时未收到，会重传 FIN。
  • TIME_WAIT（最重要的状态）：客户端发送完第四次 ACK 后进入，持续 2MSL（最长报文段寿命，通常为 2 分钟，Linux 可调整）。
    • 为什么要等 2MSL？
      1. 保证最后的 ACK 能到达服务端：若 ACK 丢失，服务端会超时重传 FIN（第三次挥手），客户端有时间重发 ACK。
      2. 让网络中残留的旧数据包消失：防止本次连接的“迷途报文”被新建立的相同 IP+端口连接错误接收。

常见面试连环炮

Q1：为什么建立连接是 3 次，关闭却是 4 次？

因为建立连接时，服务端的 SYN 和 ACK 可以合并发送（因为此时服务端无需等待上层应用准备，内核直接响应即可）。而关闭连接时，服务端收到 FIN 只表示“客户端不发数据了”，但服务端可能还有业务数据需要处理并发送，所以必须先回 ACK 应答，等应用层调用 close() 后，再发 FIN，两者无法合并。

Q2：如果第二次挥手（ACK）丢失了怎么办？

客户端在 FIN_WAIT_1 状态会启动超时重传定时器，重传第一次挥手的 FIN 包，直到收到 ACK 或达到最大重传次数后主动复位（RST）连接。

Q3：服务器大量 CLOSE_WAIT 状态堆积是什么原因？如何解决？

原因：服务器应用程序代码没有正确调用 close() 或 shutdown() 来响应客户端的 FIN 请求（比如 socket 被遗忘，没有释放）。
解决：检查服务端代码，确保在读取到 EOF 或收到 FIN 后，及时关闭对应的 socket 句柄。

Q4：TIME_WAIT 过多有什么危害？怎么优化？

危害：占用端口资源（尤其客户端端口有限）和内核内存。
优化：开启 tcp_tw_reuse（复用 TIME_WAIT 连接给新连接，需结合时间戳）或 tcp_tw_recycle（已废弃，NAT 下慎用），或调整 tcp_max_tw_buckets 限制最大数量。

三、校验和

TCP 校验和的核心作用是检测数据在传输过程中是否发生了损坏或改变，从而确保接收方得到的数据是完整的。

3.1 保护数据完整性的原理

基本流程是“发送方计算，接收方验证”：

  1. 发送方计算：发送方根据待发送的 TCP 数据（包括 TCP 头部和数据），通过特定算法计算出一个 16 位的校验和，并将其填入 TCP 头部。
  2. 接收方验证：接收方收到数据后，用同样的算法重新计算校验和。
  3. 比对结果：
    • 一致：认为数据在传输过程中是完整的。
    • 不一致：说明数据在传输过程中出现了损坏，接收方会直接丢弃该数据包。

3.2 计算流程

TCP 校验和采用“二进制反码求和”算法，步骤如下：

  1. 校验和字段置零：将 TCP 头部的校验和字段先设置为 0。
  2. 数据分组：将需要校验的数据（包括 TCP 头部、数据，以及一个重要的“伪首部”）按 16 位（2 字节） 为一组进行划分。如果数据长度为奇数，则在末尾补一个全零的字节。
  3. 累加求和：对所有 16 位的组进行二进制求和。如果最高位（第 16 位）产生进位，则需要将进位加到最低位上，这称为“循环进位”。
  4. 取反码：将上一步得到的累加和按位取反（1 变 0，0 变 1），最终结果就是校验和。

💡 什么是“伪首部”？
这是一个虚拟的 12 字节数据结构，它并不存在于实际传输的 TCP 数据包中。它包含了源 IP 地址、目的 IP 地址、协议号（TCP 为 6）和 TCP 数据包长度等信息。计算时包含这些信息，是为了让 TCP 校验和能同时检查数据包是否被错误地路由到了别处。

3.3 校验和验证的特殊性

在接收方进行验证时，计算过程与发送方相同，但会包含收到的校验和字段本身。

  • 如果数据在传输中没有出错，那么接收方计算出的最终结果将是 0。
  • 如果结果不为 0，则说明数据在传输过程中出现了错误。

3.4 局限性

  • 错误检测能力有限：TCP 使用的是 16 位校验和，存在极小的概率，数据在传输中发生了改变，但重新计算出的校验和与原来相同，导致错误无法被检测到。
  • 硬件卸载（Offloading）的干扰：现代网卡常具备“校验和卸载”功能，由硬件而非 CPU 来计算校验和。这可能导致像 Wireshark 这样的抓包工具在捕获数据包时，看到的是尚未完成计算的校验和，从而误报为“校验和错误”。这通常是正常的，不影响实际通信。

总结：TCP 校验和是保障网络通信数据完整性的第一道防线，通过发送端和接收端对数据进行“二进制反码求和”计算并进行比对，能有效地检测出绝大多数传输错误。不过，对于要求极高数据完整性的应用，通常还需要在应用层增加额外的数据完整性校验机制。

四、序列号（Seq）与确认应答（ACK）——有序性与去重机制

4.1 核心设计哲学：面向字节流

TCP 是面向字节流的协议。发送端的数据会被切分成多个数据包发送，但接收端最终交付给上层应用的必须是一个连续、无间隙、无重复的字节序列。为此，TCP 为传输的每一个字节都分配了一个唯一的逻辑编号，即序列号（Sequence Number, Seq）。

4.2 序列号与确认号的定义

概念 存放位置 含义 关键特性
序列号（Seq） TCP 头部 本报文段中第一个数据字节的序号。 仅标记起始点，包的结束边界由载荷长度决定。
确认号（Ack） TCP 头部 接收端下一个期望收到的字节序号。 代表该序号之前的所有字节均已连续收到（累计确认）。

4.3 核心机制：“起始号 + 偏移量”

误解澄清：TCP 并不是“每发送一个字节就占用一个 Seq 字段”，也不是“一个包携带所有字节的编号列表”。

实际逻辑：

  1. 包首部只写起始号：每个数据包的 TCP 头部只携带该包负载中第一个字节的 Seq 值。
  2. 包长度由 IP 层计算：接收端通过 IP总长度 - IP头长度 - TCP头长度 计算出该包的载荷长度（Len）。
  3. 偏移覆盖原则：接收端自动推算出该包覆盖的字节范围为 [Seq, Seq + Len - 1]，并计算出下一个期待序号为 Seq + Len。

举例：发送一个 Seq=1000，Len=100 的包，接收端知道它覆盖了 1000~1099，下一个期待的是 1100。

4.4 如何实现有序性

由于网络延迟不同，数据包可能后发先至（乱序到达）。

  • 接收端缓存（Out-of-Order Buffer）：接收端不会因为乱序就丢弃数据。
  • 排序算法：接收端根据每个包的 Seq 起始号 和计算出的 Len（结束偏移），将数据包插入到接收缓冲区的正确逻辑位置。
  • 交付条件：只有当缓冲区中从“期望接收的序号”开始的一段数据连续完整时，内核才会将这些数据一并交付给上层应用程序。

场景：期望 Seq=1000，却先来了 Seq=1200 的包。接收端会暂存 Seq=1200 的包，并持续发送 ACK=1000（催促重传），直到 Seq=1000 的包到达，再将 1000~1299 的连续数据一次性交付。

4.5 如何实现去重

因超时或 ACK 丢失，发送端可能会超时重传已经发过的数据包。

  • 识别依据：接收端检查新到包的 Seq + Len 区间，发现该区间内的字节在缓存中已经存在。
  • 处理动作：接收端立即丢弃这个重复的数据包（不写入应用层缓存）。
  • 反馈动作：接收端会再次回复一个 ACK，其确认号仍为当前期待的下一个连续字节序号，帮助发送端确认当前进度。

场景：已收到 1000~1099，重传包又来了 Seq=1000，Len=100。接收端识别为重复，直接丢弃，并回复 ACK=1100。

4.6 驱动重传的“确认号（ACK）”行为

ACK 机制是推动传输的“滑尺”。它通过重复确认来触发高效重传（快速重传）：

情景 接收端行为 发送端收到的 ACK
正常收到 1000~1099 缓存写入，期望 1100 ACK = 1100
包丢失（没收到 11001199，却收到了 12001299） 缓存 1200，依然期望 1100 重复的 ACK = 1100（连续收到多个）
收到重传的 1100~1199 将缓存中的 1200 拼接，期望 1300 ACK = 1300（一次性跳号确认）

注：发送端收到 3 次重复的 ACK=1100 后，会立即触发快速重传，无需等待超时。

4.7 特殊情况：SYN 和 FIN 标志也“消耗”序列号

虽然 SYN（建立连接）和 FIN（断开连接）不携带应用数据，但它们作为控制指令，也会占用一个序列号。

  • 三次握手：客户端 Seq=x（SYN 占 1 号），服务器回复 ACK=x+1，并发送自己的 Seq=y（SYN 占 1 号）。
  • 四次挥手：主动关闭方发送 Seq=z（FIN 占 1 号），被动方回复 ACK=z+1。

这确保了控制指令本身也能被可靠确认，但它们不参与应用数据的字节流拼接。

4.8 总结：Seq 与 ACK 的分工逻辑

功能维度 序列号（Seq）负责 确认号（ACK）负责
数据排序 提供排序依据（起始编号 + 长度偏移）。 告知已连续接收的边界位置。
数据去重 提供唯一区间标识（起始号 + 长度），用于发现重复。 用于确认重复包已被忽略。
丢包检测 若接收端收到的起始号 > 期望号，说明中间有包丢失。 发送端收到重复的期望号，触发快速重传。
流控基础 确定滑动窗口的左边界。 确定滑动窗口的右边界（窗口大小通告）。

🎯 一句话终极心法

Seq 负责“排座号”并指明队伍起点（首字节序号），Len（由 IP 算出）负责队伍长度，Ack 负责告诉队长“前面的人到齐了，请继续往前推进（下一个期望序号）”。三者结合，完美实现了字节流的有序拼接与重复过滤。

五、超时重传

TCP 超时重传是保障数据传输可靠性的核心机制。它的基本逻辑是：发送方每发一个数据段就启动一个定时器，若在定时器到期前未收到对方的确认（ACK），就判断数据已丢失并重新发送。这个机制的关键，就在于如何设定一个合理的“超时时间”。

5.1 核心难题：如何设定“刚刚好”的超时时间（RTO）？

这个超时时间被称为重传超时时间（Retransmission Timeout, RTO）。它不能是固定的，因为网络状况（如延迟）是动态变化的。

  • RTO 太大：丢包后要等很久才重传，效率低下。
  • RTO 太小：可能没丢包就误判重传，浪费带宽，甚至可能加剧网络拥塞。

因此，RTO 必须根据网络情况动态调整。

5.2 核心算法：如何动态计算 RTO？

  1. 测量 RTT：首先，需要测量数据从发送到收到 ACK 的往返时间（Round-Trip Time, RTT）。
  2. 计算 SRTT 和 RTTVAR：单个 RTT 样本波动大，没有参考价值。因此，TCP 会计算一个更平滑的估值，即平滑的往返时间（Smoothed RTT, SRTT），以及代表 RTT 波动程度的 RTT 变化量（RTTVAR）。
  3. 计算最终的 RTO：根据 RFC6298 标准，RTO 的计算公式为 RTO = SRTT + max(G, 4 * RTTVAR)。其中 G 是时钟粒度，4 是经验常数。这个公式既考虑了平均延迟（SRTT），也考虑了延迟的波动（RTTVAR），使 RTO 能更准确地反映网络状况。

5.3 特殊场景处理：Karn 算法与指数退避

当发生重传时，会面临一个困境：收到的 ACK，是针对第一次发送的包，还是重传的包？这会导致 RTT 测量不准，即确认二义性问题。为此，TCP 引入了两个关键机制：

  • Karn 算法：核心原则是 “发生重传时，不更新 RTT 估值”。因为此时 RTT 样本不可靠，索性忽略它，避免污染 SRTT 和 RTTVAR。
  • 指数退避（Exponential Backoff）：如果重传后仍未收到 ACK，TCP 会将 RTO 的值翻倍（例如 1 秒→2 秒→4 秒）。这就像一个“惩罚”机制，网络越不稳定，重传间隔就越长，以避免加剧拥塞。

5.4 进阶：超时重传与快速重传的协同

仅靠超时重传，响应可能不够及时。因此，TCP 引入了快速重传（Fast Retransmit） 机制作为补充。它的工作原理是：如果发送方连续收到 3 个相同的重复 ACK（表示接收方一直在期待某个丢失的包），就立即重传该包，而无需等待 RTO 超时。

这两种机制相辅相成：快速重传用于高效处理偶发丢包，而超时重传则作为兜底方案，处理更严重的网络问题。

总结：TCP 的超时重传机制通过动态计算 RTO 来适应网络变化，并依靠 Karn 算法和指数退避等策略来应对重传带来的复杂性。它与快速重传协同工作，构成了 TCP 在不可靠的互联网上实现可靠传输的基石。

六、流量控制

流量控制（防止接收方“撑爆”）的核心机制是滑动窗口协议，具体通过接收方通告的 rwnd（接收窗口，Receiver Window） 来实现。

6.1 核心机制：接收窗口（rwnd）

TCP 报文段头部有一个 16 位的“窗口”字段（rwnd），它直接告诉发送方：“我现在还有多少空闲的缓冲区容量”。

  • 发送方约束：发送方在收到确认（ACK）前，已发送但未确认的数据总量，必须严格小于或等于对方通告的 rwnd 值。
  • 动态调整：接收方根据自己的处理速度和应用层读取数据的速度，实时调整 rwnd 并携带在每一个 ACK 回复中回传。

6.2 工作流程图解（发送方视角）

假设接收方通告 rwnd = 3000 字节：

  1. 发送方连续发送数据，只要已发未确认数据 < 3000，就可以继续发。
  2. 当数据填满窗口（已发未确认 = 3000），发送方停止发送，进入“零窗口期”。
  3. 接收方处理完一部分数据（比如读走了 1000 字节），缓冲区空出空间，便在下一个 ACK 中通告 rwnd = 1000。
  4. 发送方收到该 ACK 后，窗口向右滑动，允许继续发送这 1000 字节的新数据。

6.3 生死攸关的难题：零窗口死锁（Zero Window）

当接收方缓冲区完全填满（rwnd = 0），发送方停止发送。但如果接收方后续清空了缓冲区并发送了一个 rwnd > 0 的 ACK，而这个 ACK 在网络中丢失了——此时发送方在等窗口更新，接收方在等新数据，双方将永久死锁。

解决方案（持续计时器 Persist Timer）：

  • 发送方在收到 rwnd = 0 后，启动一个持续计时器。
  • 超时后，发送方主动发送一个1 字节的探测报文（Window Probe）。
  • 接收方回复 ACK，里面携带当前的 rwnd 值。若仍有空间，发送方恢复传输；若仍为 0，计时器重置，继续等待。

6.4 流量控制 vs 拥塞控制

维度 流量控制（Flow Control） 拥塞控制（Congestion Control）
作用对象 端到端（接收方处理能力） 网络链路（路由器、带宽、延迟）
决定变量 rwnd（接收窗口） cwnd（拥塞窗口）
最终限制 发送量上限 = min(rwnd, cwnd) 发送量上限 = min(rwnd, cwnd)

打个形象的比方：
流量控制（rwnd）像是快递站门口的卸货区大小——卸货区堆满了，快递车就必须在门口等着，不能硬塞，否则仓库（缓冲区）就爆仓了。而拥塞控制（cwnd）则像是高速公路的堵车状况——高速堵了，即使你家卸货区很大，车也得在路上慢慢挪。

七、拥塞控制

7.1 地基概念

机制 管辖范围 核心痛点 控制变量
流量控制 点对点（接收方） 接收方 CPU/内存太慢，怕被喂撑。 接收窗口（rwnd）
拥塞控制 网络全局（链路/路由器） 中间马路太窄，数据包堵在缓冲区。 拥塞窗口（cwnd）

最终实际发送窗口 = min(rwnd, cwnd)

7.2 滑动窗口的“底层微操”

1. ACK 的真实含义

  • ACK 号代表“下一个期望收到的字节/包序号”，而不是“当前收到的号”。
  • 收到 ACK=3 意味着：1 号和 2 号已经全部安全到达，请发 3 号。

2. 发送方一次发几个？不等 ACK 吗？

  • 不等！ TCP 是流水线作业。只要发送窗口（cwnd）允许，发送方会一口气把窗口内所有待发数据全部背靠背扔出去（如 1、2、3、4、5）。
  • ACK 的作用不是“触发发送下一个”，而是**“触发窗口向右滑动”**。

3. 窗口怎么移动？一格一格走吗？

  • 不，是“跳跃式”飞跨！ 如果接收方收到了 1、2、3、4、5，它回复 ACK=6，发送方的窗口会直接从 [1~6] 飞到 [6~11]，一次性跨过 5 格。

4. 收到 ACK 后，到底发哪些包？（关键公式）

发送方收到 ACK 窗口滑动后，会计算可用窗口（可发新包数量）：

可用窗口 = (窗口左边界 + 窗口大小) - 下一个待发新包序号(SND.NXT)

  • 结论：窗口滑动后，发送方只填补“可用窗口”里的全新空位（如 6、7、8）。
  • 绝对不重发已经发出但还在等待 ACK 的包（如 2、3、4、5），除非触发特殊情况。

7.3 经典四大算法（Reno/NewReno）

1. 慢启动（Slow Start）

  • 阶段：刚起步或重伤重启后。
  • 规则：cwnd 从 1 开始，每收到一个 ACK，cwnd += 1（等价于每个 RTT 翻倍：1→2→4→8）。
  • 终点：达到慢启动门限（ssthresh）时，转入拥塞避免。

2. 拥塞避免（Congestion Avoidance）

  • 阶段：平稳行驶期。
  • 规则：cwnd 线性增长（每个 RTT 只加 1）。
  • 目的：缓慢试探网络极限。

3. 快重传（Fast Retransmit）

  • 触发：发送方连续收到 3 个重复的 ACK。
  • 动作：不等超时，立刻重传丢失的包。
  • 特殊权限：此操作属于“强行插队”，无视“只发新包”的常规逻辑。

4. 快恢复（Fast Recovery）

  • 触发：紧跟在快重传之后。
  • 动作（核心数学）：
    1. ssthresh = 当前 cwnd / 2（砍半）。
    2. cwnd = 新的 ssthresh（窗口直接减半，绝不归零）。
    3. 此后进入拥塞避免（线性增长）。

7.4 核心思辨——“快重传”为什么不浪费带宽？

场景：发了 1~10，3 号丢了，4、5、6 到了。

  • 接收方：收到 4、5、6，因为缺 3，连续回复 3 次 ACK=3。
  • 发送方：收到 3 个重复 ACK，此时窗口已满（SND.NXT 指向 11，但窗口右边界也是 11，没有空位发新包）。
  • 行动（快重传）：强行把“已发送队列”里的 3 号 拎出来重传。
  • 为什么不浪费 4、5、6 带宽？ 因为 4、5、6 早就被接收方缓存好了，发送方只补 3 号。重传填补了链路空缺，一旦 3 号到达，接收方回复 ACK=11，窗口瞬间飞跨，立刻发送 11、12、13…（新数据）。

7.5 终极“平行宇宙”对比——同一时刻，两种命运

重新设定：平行宇宙的起点（Time 0）

  • 拥塞窗口（cwnd） = 10（发送方一口气发出了 1~10 号包）。
  • 慢启动门限（ssthresh） = 16（因为 10 < 16，此时处于慢启动阶段，窗口还在指数增长期）。
  • 网络状况：刚刚发完这批包，等待回执（ACK）中。

分支一：轻度拥堵（触发“快重传 + 快恢复”）

命运剧本：3 号包丢了，但 4、5、6、7、8 号顺利到达接收方。

  • 接收方反应：收到 4、5、6、7、8，因为缺 3，连续发出 4 次 ACK=3。
  • 发送方动作（收到第 3 次重复 ACK 时）：
    1. 快重传：立即补发 3 号（只补这一个）。
    2. 快恢复（数学计算）：
      • 新门限（ssthresh） = 当前 cwnd / 2 = 10 / 2 = 5（注意：这里跟初始门限 16 毫无关系，只看当前窗口！）。
      • 新拥塞窗口（cwnd） = 新门限 = 5。
    3. 状态切换：因为 cwnd(5) < ssthresh(5)（相等），严格来说进入拥塞避免（线性+1 增长）。
  • 最终结果：窗口变为 5，网络负载瞬间减半，但连接不断流，继续以线性速度慢爬。

分支二：重度瘫痪（触发“超时重传 + 窗口归零”）

命运剧本：网络突然剧烈震荡，不仅 3 号丢了，连 4~10 号也全部石沉大海（或者接收方回的 ACK 全堵死在路上）。发送方苦苦等待，重传计时器（RTO）耗尽，一个有效 ACK 都没等来。

  • 接收方反应：死寂，没有任何回音。
  • 发送方动作（计时器归零瞬间）：
    1. 超时重传：重传最早未确认的 1 号（注意：这里因为不知道丢了多少，只能从头开始试探）。
    2. “归零”计算（数学计算）：
      • 新门限（ssthresh） = 当前 cwnd / 2 = 10 / 2 = 5（跟分支一的计算公式完全一样！）。
      • 新拥塞窗口（cwnd） = 1（注意：这里是强制归零后重置为 1，而不是 5！）。
    3. 状态切换：因为 cwnd(1) < ssthresh(5)，进入慢启动（指数爆炸增长，1→2→4→5）。
  • 最终结果：窗口变为 1，网速跌到谷底，以最卑微的姿态重新探测网络。

核心对比表（平行宇宙版）

对比维度 分支一：快重传（轻伤） 分支二：超时重传（重伤）
初始窗口(cwnd) 10 10
初始门限(ssthresh) 16 16
触发信号 收到 3 个重复 ACK（有动静） 计时器耗尽（死寂）
新门限(ssthresh) 10 / 2 = 5 10 / 2 = 5
新窗口(cwnd) 5（直接减半） 1（强制归零重启）
后续状态 拥塞避免（线性+1：5→6→7…） 慢启动（指数翻倍：1→2→4→5…）
隐含意义 网络虽堵但通，保留现有连接。 网络彻底死机，必须“挂一档”重来，防止崩溃。

为什么门限都变成 5，但窗口却差这么多？

这是 TCP 最精妙的设计哲学：

  • 门限（ssthresh） 记录的是**“这次事故的严重水位标记”**。既然当前窗口是 10 时出的事，那么门限就永久记录为 5（10 的一半），作为未来永远不能轻易逾越的“警戒线”。
  • 窗口（cwnd） 则根据伤情严重程度决定起跑线：
    • 如果是轻伤（快恢复）：说明后半段路还能跑，直接从 5 开始跑（起跑线就是终点线）。
    • 如果是重伤（超时）：说明路全断了，必须从 1 开始慢慢试探（起跑线在起点）。

7.6 现代“高智商”黑科技

1. BBR（谷歌出品）

  • 传统算法痛点：依赖“丢包”判断，导致缓冲区膨胀（延迟暴增）。
  • BBR 逻辑：不看丢包，只看带宽最大值和延迟最小值。把数据量控制在“刚好填满管道，绝不溢出缓冲区”的完美平衡点。
  • 效果：高带宽 + 极低延迟（YouTube 在用）。

2. 显式拥塞通知（ECN）

  • 传统痛点：非要等到丢包才减速（太粗暴）。
  • ECN 逻辑：路由器发现快堵了，直接在 IP 包头部打上“拥塞标记”（电子罚单），发送方提前主动减速，根本不需要丢包。

7.7 终极大招——如果超时重传的包又丢了怎么办？

如果超时后重传的 1 号 又超时了：TCP 会启动二进制指数退避（Binary Exponential Backoff）。下一次重传的等待时间（RTO）会变成原来的 2 倍、4 倍、8 倍……直到放弃连接。这是为了防止全网在拥堵时拼命重传，导致雪上加霜。

终极背诵心法

滑动窗口流水线，累积确认跨格跳；
慢启动来指数涨，拥塞避免加一跑；
三个重复快重传，只补丢包不瞎搞；
窗口减半快恢复，不归零来保命好；
若遇超时全归零，挂回一档慢慢找；
BBR 看带宽延迟，ECN 提前打报告！

八、粘包问题

TCP 是面向字节流的协议，它只管可靠地传输字节，没有消息边界。这就导致发送方发的东西，接收方读的时候会出现“多读”或“少读”的情况：

  • 粘包：发送方发了两个独立包（如 “Hello” 和 “World”），接收方一次性读到了 “HelloWorld”（多读了）。
  • 拆包：发送方发了一个大包（如 “HelloWorld”），接收方两次才读完，第一次读到 “Hello”，第二次读到 “World”（少读了）。

处理这个问题的核心只有一条铁律：“应用层必须自己定义消息边界”。业界主要有以下三种标准解法，按推荐程度从低到高排列：

8.1 固定长度（Fixed Length）

规定每个报文固定长度（例如 1024 字节），不足的用空字符（\0）补足。

  • 实现：接收方每次只读取固定字节数，读到就是一个完整消息。
  • 缺点：极其浪费带宽，且如果业务数据超过固定长度，无法处理。
  • 现状：几乎不用，仅用于极其简单的内部调试。

8.2 特殊分隔符（Delimiter）

使用特殊字符作为消息的结束标志（如 HTTP 的 \r\n\r\n，或自定义的 \n）。

  • 实现：接收方循环读取，每次检查缓冲区中是否包含分隔符，如果找到则截取分隔符之前的数据作为一个完整包。
  • 缺点：业务数据本身不能包含分隔符，否则需要转义（如将 \n 转成 \\n），增加了编解码的复杂度。
  • 适用：文本协议、命令行交互。

8.3 自定义头部+负载（Length Field）—— 工业界最标准做法

在消息开头固定几个字节用来声明整个消息的总长度。

  • 结构：[4 字节消息总长度] + [消息体（Protobuf/JSON/二进制）]
  • 处理逻辑（重点）：
    接收方维护一个动态缓冲区，进行如下状态机处理：
    1. 检查缓冲区长度是否 >= 4。若不足，等待下一次读事件（不读取）。
    2. 若够，读取前 4 字节，解析出 Payload Length = N。
    3. 检查缓冲区总长度是否 >= 4 + N。
    4. 若不足，依然等待，不读取业务数据。
    5. 若够，从缓冲区中截取出完整的 N 字节作为独立业务包，并从缓冲区中移除已处理的数据（处理剩余粘包数据）。

工程落地最佳建议

  • 不要自己造轮子：除非是学习目的，线上项目请直接使用成熟的网络框架（如 Netty、Mina）。
  • Netty 内置解码器：直接添加 LengthFieldBasedFrameDecoder，只需配置几个参数（最大长度、长度字段偏移量、长度字段字节数），Netty 自动帮你处理粘包拆包，拿到就是完整消息。
  • 编码选型：消息体强烈建议使用 Protobuf（Protocol Buffers），体积小、解析快，且自带二进制安全，天然适合与“长度字段”配合。

如果你是在面试中回答这个问题，核心得分点是：强调 TCP 是流式协议，根本原因是接收方不知道消息界限；解决方案是 “长度字段 + 状态机”，并且一定要讲出“不够时就 return/等待，不要强制读取”的细节。

九、队头阻塞问题

TCP 的队头阻塞（Head-of-Line Blocking, HoL 阻塞），是指当 TCP 连接中的一个数据段丢失或乱序到达时，接收方必须阻塞后续所有数据的交付，直到丢失的那个数据段被成功重传并收到为止。

9.1 为什么会产生阻塞？（核心机制）

TCP 提供的是可靠的、按序的字节流服务。接收方的协议栈内部维护着一个重排缓冲区。

  • 正常情况：数据包按序到达（1, 2, 3），内核直接交给应用层。
  • 阻塞发生：假设包 1 到达，包 2 在网络中丢失了，但包 3 和包 4 随后到达了。
    • 因为 TCP 要求“按序交付”，内核不能把不连续的 3、4 交给应用层（否则应用层会读到残缺的数据）。
    • 内核会把 3 和 4 暂存在重排缓冲区中，然后持续发送 ACK 确认号（确认号一直指着包 2），催促发送方重发包 2。
    • 在包 2 成功到达之前，即使包 3、包 4 的数据已经躺在网卡里了，应用层进程也读不到它们。这就是“队头”被“头部的包”堵住了。

9.2 最大痛点：丢包延迟（RTT 依赖）

队头阻塞的严重程度取决于重传时间：

  • 超时重传（RTO）：如果发送方没收到针对包 2 的重复 ACK，直到计时器超时才重传，这通常会耗费 几百毫秒甚至秒级 的时间。在此期间，后续所有数据都在排队等待，造成应用层明显的卡顿。
  • 快速重传（Fast Retransmit）：如果接收方持续发重复 ACK，发送方可以在超时前重传，但这依然需要 至少 1 个 RTT（往返时延） 的时间来等待补发。

形象类比：就像在收费站排队，第一辆车（包 2）发现没带钱（丢失），后面的车（包 3、4）虽然钱都准备好了，但必须等第一辆车补完手续费开走，整条车队才能动弹。

9.3 为何在 HTTP/2 时代尤其致命？

  • HTTP/1.1 的队头阻塞是应用层的（一个连接只能同时发一个请求，请求排队）。
  • HTTP/2 引入了多路复用（多个请求在一个 TCP 连接上并发）。然而，HTTP/2 的多个“流”是共享底层这一个 TCP 连接的。
  • 致命打击：如果这个 TCP 连接上发生了任意一个丢包（无论丢的是哪个请求的数据），所有复用在这个连接上的 HTTP/2 请求（包括那些完全不相关的图片、CSS、API 请求）都会被全部阻塞，直到丢包重传完成。这就是所谓的“在单一 TCP 连接上共享拥塞控制和可靠性所带来的副作用”。

9.4 解决方案：QUIC（HTTP/3）

正因为 TCP 的 HoL 阻塞是操作系统内核层面写死的规则（必须按序交付），应用层无法绕过，所以谷歌主导开发了 QUIC 协议（基于 UDP）。

  • QUIC 在应用层实现了类似 TCP 的可靠传输，但粒度更细。
  • 它支持 流级别的独立控制：如果同一个连接上，流 A 丢包了，只会阻塞流 A 自身的重排，流 B 和流 C 的数据完全不受影响，可以直接交给上层处理。
  • 这正是 HTTP/3 抛弃 TCP，转用 QUIC 的核心原因之一。

总结一句话：TCP 的队头阻塞是由“强制按序交付”导致的，丢失一个包会导致其后所有已到达的数据在缓冲区“干等”，而在高丢包率或高延迟的弱网环境下，这种阻塞会严重拖垮 HTTP/2 的多路复用性能。
